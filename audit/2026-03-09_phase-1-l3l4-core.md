**Date:** 2026-03-09

## Summary

Phase 1 implements the Layer 3/4 DDoS protection core for JZap. This includes
full eBPF/XDP kernel programs for packet-level filtering, a Rust userspace
manager that loads and controls the eBPF programs via the aya library, and a
set of sidecar modules that provide metrics export, control-plane sync,
traffic baseline anomaly detection, and structured logging.

## Architecture Decisions

1. **Platform-conditional compilation**: The eBPF loader uses `#[cfg(target_os = "linux")]`
   to provide real aya-based implementation on Linux and no-op stubs on other platforms.
   This allows `cargo check` and CI to pass on all platforms.

2. **SKB_MODE default**: XDP programs attach with `XdpFlags::SKB_MODE` by default for
   broader NIC compatibility. Production deployments on supported NICs should switch to
   `DRV_MODE` or `HW_MODE` for 10x+ performance.

3. **Full-sync blocklist model**: The blocklist sync does a complete replacement each
   cycle rather than incremental diffs. The control plane sends the entire active
   blocklist, and the loader overwrites all entries. This simplifies consistency at the
   cost of slightly higher sync overhead (acceptable for <1M entries).

4. **N-sigma baseline**: The anomaly detector uses a rolling window of 120 samples
   with a configurable sigma threshold (default 3.0). A critical threshold is 2x the
   warning threshold (6-sigma). This provides a simple but effective early-warning system
   for volumetric attacks.

5. **Broadcast channel for anomalies**: Anomaly events use `tokio::sync::broadcast`
   so multiple consumers (traffic logger, future alert system, future webhook) can
   receive events independently without blocking.

## Known Limitations

- eBPF programs cannot be compiled on Windows (expected — `linux/bpf.h` unavailable)
- Rust workspace shows LSP errors for `aya` crate on Windows (expected — linux-only dep)
- Python control-plane LSP errors persist (redis.asyncio, alembic not installed locally)
- Docker is not available on this Windows machine; Dockerfile changes untested locally
- The eBPF loader's `Mutex<HashMap<XdpProgram, Ebpf>>` uses an explicit unsafe `Send + Sync`
  impl because `aya::Ebpf` may not implement Send automatically — this should be
  reviewed for correctness in a Linux CI environment
- Integration test scripts require `hping3` (falls back to netcat/ping if unavailable)
